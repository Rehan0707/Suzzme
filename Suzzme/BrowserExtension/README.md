# Suzzme Chrome browser bridge

Step 14 implements a Chrome Manifest V3 extension, compiled Swift Native Messaging host, signed-peer XPC broker and app-owned pairing UI. Chrome is the supported target. Safari requires a separate Safari Web Extension/native-app target and is unavailable here. Chromium installations are not accepted by the installer in this pass.

The Chrome extension supports explicit requests for GitHub, LinkedIn, Notion, and Slack. Optional automatic tab prompts are off by default. When enabled from the extension popup, Chrome asks for host access only to those supported HTTPS sites; tab activation is checked by hostname, and only the service ID (or canonical GitHub repository slug) crosses the authenticated native bridge. Query strings, fragments, page content, provider accounts, tokens, model requests, writes, and authorization grants are excluded. The extension rechecks active-tab identity, ignores incognito/loading tabs, and invalidates on navigation. General page/selection sharing remains disabled. Safari Web Extension pairing is not implemented. The separate native URL-only Share extension for iOS/macOS is described in [SHARE_HANDOFF.md](../SHARE_HANDOFF.md); it requires owner signing/App Group setup and explicit URL review.

## Build and configure

Xcode's macOS build phase compiles `SuzzmeBrowserHost` and `SuzzmeBrowserBroker` into `Contents/MacOS`, and packages the LaunchAgent plist under `Contents/Library/LaunchAgents`. iOS builds skip these components. Neither Node nor a runtime shell launcher is used. Building never registers the agent or installs a Chrome manifest.

`BrowserNativeHost/BrowserBridge.json` deliberately contains empty configuration. Supply the **real** signing Team ID, provisioned macOS App Group (with that Team prefix), and installed Chrome extension ID (32 letters a–p), using this file or the `SUZZME_BROWSER_CONFIG` Xcode build setting. These identifiers are public configuration, not secrets. No extension identifier is fabricated.

The app, broker and host must be genuinely signed with the configured Team and exact identifiers `rehan.Suzzme`, `rehan.Suzzme.BrowserBroker`, `rehan.Suzzme.BrowserHost`. Add the provisioned App Group entitlement to the app's development and release entitlements; helper entitlements are generated by the build phase. Keep existing sandbox entitlements. Ensure sandbox Mach services named `<AppGroup>.browser.registration` and `<AppGroup>.browser.host` are permitted by the provisioned group. Nested tools are signed only when Xcode signing is enabled. Current unsigned development builds fail closed.

Prepare the manifest using:

```
python3 BrowserNativeHost/prepare-chrome-manifest.py --app /absolute/path/Suzzme.app --extension-id REAL_EXTENSION_ID --output /chosen/path/rehan.suzzme.browser_context.json
```

The generator verifies the app and both nested signatures and emits an exact `allowed_origins` entry. It does not install anything. With user participation, install the reviewed manifest under `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/`. Load/publish the extension through the appropriate Chrome developer/distribution workflow and verify its actual ID first. Do not read browser profiles or manufacture an ID. User registration/approval of the app-owned LaunchAgent occurs through **Settings → Integrations → Browser pairing → Enable browser helper**, using `SMAppService`; Login Items approval may be required. No privileged helper is used.

## Pair and request

1. Open the signed, configured Suzzme app. Enable the helper explicitly.
2. Choose the configured installed extension and approve pairing for two minutes.
3. Copy the one-use 32-byte code only into that extension's pairing form. Never into a URL, terminal or chat.
4. The app validates approval, extension identity, expiry and five-attempt bound. Pairing records live atomically in non-syncing, unlocked-device Keychain storage. Chrome's key is in trusted extension-local storage, never page/content-script storage.
5. Either enable **Automatic tab prompts** and grant the supported-site permissions in Chrome, or open the extension on a supported tab and request the connection manually. The native handoff carries the app name or a canonical GitHub repository slug only. A one-use server challenge expires after eight seconds; both sides authenticate literal payload bytes with HMAC-SHA256. Request IDs, task ownership, 30-second observation age, context tombstones and frame/schema limits are enforced.
6. Existing Presence shows No / Not now / Yes. Yes opens that service’s connection setup only. Provider sign-in and account access remain separate and require the service’s supported authorization flow.
7. Revoke all pairings in Suzzme to delete the transport keys, close the old listener epoch and retire its pending request. Forget in Chrome removes only that browser's key. Restart drops challenges/leases; approved pairings remain in Keychain.

## Native facilities and boundaries

Chrome starts the executable and transports 4-byte native-endian length-prefixed JSON over STDIO. The app cap is 65,536 bytes, exact reads reject truncation, input and XPC lifetime are bounded by the host's five-second process deadline, and stdout carries framed JSON only. No secrets/error bodies are logged. The host validates Chrome's supplied origin against the signed configuration; origin text alone is not authentication.

The `SMAppService` broker exposes separate registration and lookup Mach services with code-signing requirements enforced **before** XPC delegate acceptance. Only the app can register an anonymous listener endpoint; only the host can obtain it. The anonymous app listener independently requires the host identity; outgoing connections require the broker/app identity. The broker carries an opaque endpoint only, no content or credentials, and retires it with registration loss. Pairing HMAC adds extension-bound authentication. No anonymous XPC endpoint is archived into a file.

Legacy `suzzme://browser/github` links remain unprivileged setup requests; knowing a URL scheme never establishes browser pairing or account access. The shipping popup uses Native Messaging, not that legacy path.

Official platform references reviewed: [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [NSXPCConnection peer signing requirement](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:)), [SMAppService LaunchAgent](https://developer.apple.com/documentation/servicemanagement/smappservice/agent(plistname:)). APIs were also checked against installed macOS 27 SDK headers; deployment remains macOS 14.
